# Build and Deploy a Complete Self-Hosted Electronics Inventory Application

You are an expert Flutter, FastAPI, PostgreSQL, Docker, Linux, security, and deployment engineer.

Create and deploy a complete self-hosted application called:

# Tech Panda Components Inventory

The application will be used by an electronics hobbyist and YouTube creator to manage approximately 500–2,000 electronic components, modules, development boards, tools, consumables, and project stock.

The application must work on:

* Android phones and tablets
* Windows computers through a web browser
* Linux and macOS web browsers where needed
* An optional installable Progressive Web App where supported

The user already has an always-online Linux computer with SSH access enabled.

All application data must be hosted on the user’s Linux computer.

Do not use:

* Firebase
* Supabase
* AWS
* Google Cloud
* Azure
* MongoDB Atlas
* Any required paid cloud database
* Any required external image-storage service
* Any required external authentication service

The entire application must remain functional using the user’s own Linux computer.

Build the complete application, test it, configure Docker deployment, connect to the Linux server through SSH when deployment credentials are available, deploy the system, run database migrations, create the administrator account, perform health checks, and report the final deployment result.

Do not stop after generating an outline or sample code.

---

# 1. Main Objectives

The application must allow the user to:

1. Add electronic components and modules.
2. Categorize different types of components.
3. Store category-specific technical specifications.
4. Add components with or without pictures.
5. Add multiple components to stock in one transaction.
6. Remove multiple components from stock in one transaction.
7. Associate consumed components with projects and YouTube videos.
8. Return unused components to inventory.
9. Record damaged, lost, or discarded components.
10. Perform physical stock counts.
11. Adjust stock without destroying transaction history.
12. Find components with minimal keyboard input.
13. Scan component and storage-location QR codes.
14. Access the same inventory from Android and Windows.
15. Cache inventory locally for offline viewing.
16. Prepare stock transactions while offline.
17. Synchronize offline drafts when the server becomes available.
18. Store component pictures on the Linux server.
19. Create automatic database and image backups.
20. Export reports as CSV, JSON, and PDF where appropriate.

This is primarily a private, single-owner application.

Design the database so additional users can be added later, but do not create unnecessary enterprise complexity.

# 4. SSH Deployment Configuration

Codex must support automatic deployment through SSH.

Create `.env.deploy.example` with:

```text
INVENTORY_SSH_HOST=
INVENTORY_SSH_PORT=22
INVENTORY_SSH_USER=
INVENTORY_SSH_KEY_PATH=
INVENTORY_REMOTE_DIR=/opt/tech-panda-inventory

INVENTORY_DEPLOYMENT_MODE=tailscale
INVENTORY_TAILSCALE_HOSTNAME=tech-panda-inventory
TAILSCALE_AUTHKEY=

INVENTORY_PUBLIC_DOMAIN=
INVENTORY_ADMIN_NAME=Arslan
INVENTORY_ADMIN_EMAIL=
INVENTORY_ADMIN_PASSWORD=

INVENTORY_TIMEZONE=Asia/Karachi
INVENTORY_DEFAULT_CURRENCY=CNY
INVENTORY_BACKUP_RETENTION_DAYS=30
INVENTORY_WEEKLY_BACKUP_RETENTION=12
```

Rules:

* Never commit `.env.deploy`.
* Never commit an SSH private key.
* Never print passwords, private keys, database passwords, JWT secrets, or Tailscale authentication keys in logs.
* Prefer the existing SSH agent.
* Use `INVENTORY_SSH_KEY_PATH` only when explicitly configured.
* Set secret-file permissions to `600`.
* Test SSH access using non-interactive mode before deployment.
* Do not repeatedly request an SSH password.
* Do not place the Linux user’s password into scripts.
* Use `sudo` only for required server bootstrap operations.
* Detect whether passwordless sudo is available.
* If the remote account cannot run required sudo commands, generate a single safe bootstrap command for the user instead of storing the sudo password.

Test SSH using a command similar to:

```bash
ssh -o BatchMode=yes \
    -p "$INVENTORY_SSH_PORT" \
    "$INVENTORY_SSH_USER@$INVENTORY_SSH_HOST" \
    "echo SSH_CONNECTION_OK"
```

Do not continue with remote modifications if the SSH test fails.

# 7. Deployment Modes

Support two deployment modes.

## Mode A: Tailscale Private Deployment

This is the recommended default.

Requirements:

* The Linux server joins the user’s Tailscale network.
* Android and Windows devices connect through Tailscale.
* The inventory application is not publicly exposed.
* Do not require router port forwarding.
* Use a stable Tailscale hostname.
* Use HTTPS supported by the current Tailscale configuration.
* Verify that the application can be opened through the Tailscale hostname.
* Do not log or commit a reusable Tailscale authentication key.
* Remove or expire temporary deployment keys where appropriate.

The deployment script should:

1. Detect whether Tailscale is installed.
2. Install it using an official supported installation method if permitted.
3. Check whether the server is already authenticated.
4. Use `TAILSCALE_AUTHKEY` only if supplied securely.
5. Configure the requested hostname.
6. Determine the current private hostname or address.
7. Configure private HTTPS access using supported current Tailscale commands.
8. Verify connectivity locally.

Do not replace an existing Tailscale configuration without confirmation.

## Mode B: Public Domain Deployment

Use this only when `INVENTORY_PUBLIC_DOMAIN` is configured.

Requirements:

* DNS must point to the Linux server.
* Ports 80 and 443 must reach the server.
* Caddy should obtain and renew HTTPS certificates.
* Redirect HTTP to HTTPS.
* Apply stricter login protection and rate limiting.
* Do not expose PostgreSQL.
* Do not expose internal Docker ports.
* Validate the domain before deployment.

Do not generate self-signed certificates for normal Android production use.

# 13. Inventory Transaction Rules

Never update component stock directly from normal CRUD endpoints.

All stock changes must go through a dedicated inventory service.

Required operations:

* Opening Stock
* Stock In
* Stock Out
* Project Consumption
* Return
* Adjustment Increase
* Adjustment Decrease
* Damaged
* Lost
* Discarded
* Transfer
* Reversal

Create a backend service with methods similar to:

```python
create_opening_stock()
commit_stock_in()
commit_stock_out()
commit_project_consumption()
commit_return()
commit_adjustment()
commit_damage()
commit_loss()
commit_transfer()
reverse_transaction()
```

All multi-component transactions must:

1. Require authentication.
2. Check user permission.
3. Validate the request.
4. Reject an empty cart.
5. Limit one transaction to 100 unique components.
6. Merge duplicate component lines.
7. Reject zero quantities.
8. Reject invalid negative quantities.
9. Begin one PostgreSQL transaction.
10. Lock all affected component rows using `SELECT ... FOR UPDATE`.
11. Lock rows in a consistent order to reduce deadlocks.
12. Validate every component.
13. Reject missing components.
14. Reject archived components.
15. Calculate quantity before and after.
16. Check insufficient stock.
17. Reject the complete transaction if any line fails.
18. Create one transaction header.
19. Create all movement lines.
20. Update every affected component.
21. Commit all changes together.
22. Roll back all changes if any operation fails.
23. Return the committed transaction summary.
24. Record an audit event.

No component quantity should change if one line in the cart fails.

---

# 14. Idempotency and Duplicate Protection

Every stock transaction request must contain a UUID idempotency key generated by the Flutter client.

The backend must:

* Store the idempotency key.
* Reject or safely return an existing transaction if the same key is submitted again.
* Never change stock twice for one idempotency key.
* Handle client retries safely.
* Handle internet interruptions during submission safely.

If the first request committed but the response was lost, retrying the same request must return the original committed transaction.
